# 網頁版美術升級：從程式畫的 16px 換成 AI 生成的 32px

這份是**操作手冊**，回答五件事：用什麼工具、生成什麼、檔案多大、放哪裡、怎麼看成果。
風格規格與完整需求清單見 `roguelike_art_guide.md`（那份是為 Godot 版寫的，
規格通用；這份只講網頁版的接法與遷移順序）。

> **動畫 v2：** 角色現在支援走路換腳、三段攻擊與受擊後仰。正式逐格圖集契約見
> [`art_animation_spec.md`](art_animation_spec.md)，可直接使用的生成提示詞見
> [`art_prompts_hero.md`](art_prompts_hero.md)、[`art_prompts_mon.md`](art_prompts_mon.md)
> 與 [`art_prompts_boss.md`](art_prompts_boss.md)。舊 32/48px 靜態圖保留作 fallback。

## 0. 先決定的三件事（已經替你決定好，理由在後面）

| 項目 | 決定 | 理由 |
|---|---|---|
| 尺寸 | **怪物 32×32；主角與頭目 48×48** | 主角是玩家長時間注視的焦點；見下方尺寸說明 |
| 遷移方式 | **提高算圖解析度，不動邏輯格子** | 見第 4 節。這是整份文件最重要的一段 |
| 交接方式 | **原圖丟進 repo 的 `art_raw/`** | 對話裡貼的圖存不進硬碟，跑不了轉檔工具 |

### 為什麼從 24 改成 32

這份文件原本寫 24，理由是「面積夠、重畫成本比 32 低一半」。
第一批圖轉完之後改掉了，因為有兩件事只有真的轉過才會知道：

1. **模型畫的細節密度本來就在 32 這個級距。** 同一張原圖轉 24 和轉 32 排在
   一起看，24 的骷髏沒有臉、哥布林的眼睛糊成一團 —— 不是轉檔壞掉，是
   24 格裝不下它畫的東西。要在 24 好看，得回頭要求模型畫得更簡，
   等於把「畫得好看」的難度推給提示詞。
2. **32 的縮放倍率是整數。** 邏輯格子是 16，24 要 1.5 倍、32 要 2 倍。
   遷移期間一定會有一半的東西還是程式畫的 16px 舊圖，1.5 倍會把它們
   重取樣成半個像素、糊掉而且糊得不平均；2 倍則是原樣放大，清清楚楚。
   這條在寫這份文件的時候沒想到，但它比第 1 點更硬 ——
   它決定的是「遷移過程中專案好不好看」，而遷移會持續很久。

要退回 24 的話只有一個地方要改：`tools/pixelize.py` 的 `TILE`，
以及第 4 節的算圖倍率。原圖不用重生成。

## 1. 用什麼工具生成

任何影像模型都可以，差別只在一致性：

| 工具 | 適合 | 注意 |
|---|---|---|
| ChatGPT（圖像） | 一次生一張 sheet，可以對話微調 | 最容易「照著指示改」，首選 |
| Midjourney | 風格最漂亮 | 不太聽尺寸與網格指令，要多試 |
| Firefly | 商用授權最乾淨 | 像素風偏弱 |

**都不要求它輸出 32×32。** 它做不到，也不需要——它輸出 1024×1024，
`tools/pixelize.py` 會負責降到 32 並統一色盤。

**也不要求它排整齊的網格。** 它不會照做，而且每一批的排法都不一樣。
第一批那張 2×2 就是：史萊姆的下緣壓過水平中線、骷髏的頭蓋骨正好從中線開始，
按網格硬切的結果是史萊姆下面多一塊白球、骷髏差點被切到頭。
`--auto` 改成用連通元件自己找角色，排得多亂都無所謂。

上面這段只適用於「一張圖裡有多隻不同角色」的舊靜態母稿。動畫圖集必須嚴格使用
10x3 固定格位，且一次只做同一名角色；否則遊戲無法知道哪格是腳步、攻擊或受擊。

## 2. 生成什麼（第一批只做四隻）

不要一開始就做六十張。**第一批只驗證管線**：四隻怪、一張 2×2 sheet。

滿意了再照這個順序往下：怪物 → 地形 → 道具 → 主角。
主角放最後，因為它是玩家盯最久的東西，而那時候你已經知道這條管線的手感了。

## 3. 檔案大小與命名

| 項目 | 規格 |
|---|---|
| 生成的原圖 | 1024×1024 或 2048×2048 PNG，越大越好（降取樣才有平均可算） |
| 背景 | 白色或透明皆可，**不要**漸層背景 |
| 存放 | `art_raw/<批次名>.png`，例如 `art_raw/mon_batch1.png` |
| 轉檔後 | 由 `pixelize.py` 產出 32×32 PNG，自動放進 `web/art/` |
| 單張成品 | 32×32，32 色以內，通常 1～2 KB |

動畫成品另計：怪物為 `320x96`、目標不超過 32 KB；主角與頭目為
`480x144`、目標不超過 64 KB。禁止把 1024px 生成原圖直接放進
`web/art/anim/`。

## 4. ★ 怎麼從 16 換到 32 而不炸掉整個專案

這是最重要的一段。**不要去改 `T = 16`。**

現在整個美術層是照 16 寫死的：精靈資料是 16 字元寬的字串、主角身上的武器
是用固定座標畫的、地磚、光影、名牌位置全部吃這個數字。改它等於同時
拆掉美術層與版面層，而且中間任何一刻專案都跑不起來。

**正確做法：邏輯格子維持 16，把「算圖解析度」拉高。**

```
現在：畫布內部 224×160，一格 16px，視野 14×10 格
之後：畫布內部 448×320，一格 16 邏輯單位 × 2 算圖倍率 = 32 實際像素
```

實作上是在每一幀開頭加一行縮放變換，**所有既有的繪圖座標一個字都不用改**——
它們算的是邏輯座標，乘算交給變換矩陣。32px 的圖畫進 16 邏輯單位的格子裡，
在 2 倍的畫布上剛好是 1:1 的像素，不會糊。

這樣做的好處：

- 視野格數不變（手機上看到的房間一樣大）
- 名牌、小地圖、版面、九種視窗尺寸的測試全部不受影響
- **可以一張一張換**：載到圖就用圖，沒載到就用現在程式畫的（放大 2 倍）。
  中間任何時刻專案都跑得起來，這是能不能做完的關鍵
- 倍率是整數 2，舊的 16px 程式畫圖放大時是原樣複製，不會被重取樣糊掉

要再往上換成 64 也是同一個機制，倍率改成 4。

## 5. 怎麼看成果

三層驗收，由快到慢：

```bash
# 1. 轉檔時就檢查色盤合不合規（秒級）
python3 tools/pixelize.py --check web/art

# 2. 美術驗收頁：所有精靈排在一起，看有沒有哪一張出戲
python3 tools/build_sprite_sheet.py && open web/sprite_sheet.html

# 3. 實機：直接開遊戲，在手機尺寸看實際大小
```

第 2 步是重點。**單看一張圖永遠是好看的，排在一起才看得出風格有沒有跑掉。**

## 6. 第一批的提示詞（直接複製貼上）

貼進 ChatGPT 的圖像生成、Midjourney 或 Firefly 都可以。
如果工具支援參考圖，把 `docs/art/palette.png` 一起附上。

```
一張 2x2 網格的像素美術精靈表，共 4 個獨立角色，白色背景，格子之間留白，
四格等大、每個角色置中。

風格：SNES 時代 16-bit 俯視角地牢探索遊戲的敵人精靈。
正面略帶 3/4 俯視、面向鏡頭。硬邊像素、零抗鋸齒、厚實深色外框
（外框用深褐或深藍，不要純黑）、固定左上光源、右下留暗面。
每個角色 6~10 色。縮到 32x32 仍然認得出是什麼 —— 剪影優先於細節。

四個角色依序為：
01 洞穴鼠：小型、低威脅，圓耳長尾，土棕色，教學用的第一隻怪
02 藍史萊姆：半透明的藍色黏液團，沒有明確的面向感，呆滯
03 綠哥布林：綠皮膚、背著布袋，手上抓著搶來的東西，表情狡猾
04 骷髏兵：白骨、破舊胸甲、手持缺口短劍，空洞的眼窩

重要：四隻的剪影必須明顯不同（高矮、寬窄、有沒有武器一眼分得出來）。
不要文字、不要編號、不要地面投影、不要背景元素、不要漸層。
```

**收到圖之後你要做的**：上傳到 `art_raw/`（GitHub 網頁上傳即可，檔名隨便），
然後告訴我。剩下的轉檔、接進遊戲、排驗收頁我來做。

剩下 34 隻的提示詞在 **`art_prompts_mon.md`**，已經分成六批寫好，
一次貼一批。那份也記著「站姿要貼齊底部」這一條 —— 第一批沒寫，
結果趴著的洞穴鼠浮在自己的影子上方四格。

## 7. 一句話總結流程

```
生成 1024px 大圖  →  丟進 art_raw/  →  pixelize --auto 降成 32px 統一色盤
   →  接進 atlas（載不到就用舊的）  →  驗收頁排排看  →  實機確認
```

每一輪只做一批，每一批都跑完整條流程。
**不要囤圖**——囤到最後才發現風格不對，是這種專案最常見的死法。

## 8. 一張一張載，會不會太慢？（量過了，不會）

擔心的是：現在 44 張圖就是 44 個請求，全部做完會超過 100 個。
量了才知道問題不在那裡。

| | 4G | 慢速 3G |
|---|---|---|
| 只有 index.html | 1.50s | 13.0s |
| 加上 44 張圖 | 2.09s | 15.7s |
| **圖的成本** | **+0.6s** | **+2.7s** |

而且那 0.6s 是加在 `load` 事件上，不是加在「玩家看到畫面」上 ——
封面是腳本畫的，圖在背景平行載，載到才換。**玩家不會等圖。**

真正佔位置的是 index.html 自己：628 KB（gzip 後 230 KB）。
美術全部加起來只有 55 KB，平均一張 1270 位元組。
換句話說，美術佔了 44/45 的**請求數**，但只佔 19% 的**位元組**。
而且上面那組數字是本機 HTTP/1.1、沒有壓縮量的，
GitHub Pages 有 HTTP/2 多工與 gzip，只會更快。

**所以不要為了省請求數去打包 sprite atlas。** 打包會失去這條管線最重要的
性質：一張一張換、載不到就用舊的、中間任何時刻都跑得起來。
那個性質是這次遷移能做完的原因，不值得拿來換 0.6 秒。

要重新評估的門檻：**圖超過 300 張，或美術總量超過 1 MB。**
到那時候再打包也不遲，而且那時候風格早就定案了。

## 9. 兩種形態：網站版與單檔版

美術一張一張載，是為了「一批一批換」——那是這次遷移能做完的原因。
但這款遊戲的識別一直是「一個檔案打開就能玩」，而 59 個外部檔案破壞了它。

所以兩種都有：

```bash
# 網站版：web/ 原封不動送上 GitHub Pages，圖照 URL 一張一張載
# 單檔版：把每一張圖轉成 data URI 內嵌
python3 tools/build_single.py            # → dist/index.html（約 720 KB）
```

遊戲那邊只多一行 `im.src = ART_DATA[id] || url`，網站版完全不受影響。

單檔版還順手解掉一個限制：**data URI 不會污染畫布**。
外部 PNG 在 `file://` 底下會讓 getImageData 丟 SecurityError，
於是頭目的金邊與背光、影子的著地量測全部退化；
內嵌之後這些在本機雙擊打開也完全正常。

CI 會跑一次打包當作檢查 —— 那個 ART_DATA 鉤子被改名的話，
網站版一切正常、打包卻壞掉，不跑就要到要散佈的那天才發現。

## 10. 主角是唯一不能「一張換一張」的東西

怪物、頭目、道具都是一張圖換一張圖。主角不是 —— 它是**四層疊出來的**：

```
身體（六種體型 × 十種顏色）＋ 帽子（九種職業）＋ 盾（六面）＋ 武器（八把）
= 25920 種組合
```

不可能一張一張畫，而且分層本身就是玩法：帽子決定職業、手上那把劍決定
「我變強了」、體型與顏色是玩家自己選的「這是我的角色」。
換成一張畫得再好的主角圖，都只會是「某個角色」。

所以主角這一批換的是**每一層**，不是整個角色：

| 層 | 檔案 | 張數 | 怎麼換顏色 |
|---|---|---|---|
| 身體 | `art/hero/<體型>.png` | 6 | 色階置換（見下） |
| 帽子 | `art/hat/<id>.png` | 9 | 不換 |
| 武器 | `art/weapon/<id>.png` | 8 | 不換 |
| 盾 | `art/shield/<id>.png` | 6 | 不換 |

### 十種顏色只畫一張圖：色階置換

身體的動畫原圖只畫陶土色，成品使用十色體積色盤：外框 `#0d0d12`，
由最深暗面到高光依序為 `#6b2618`、`#a8452c`、`#c95b31`、`#d97757`、
`#e87a4a`、`#f5a95e`、`#eaa88c`、`#f6c4a2`，以及眼白 `#f2efe7`。
這讓 48×48 主角能保留連續亮面、中間色與右下核心暗面，不再因五色壓縮而變平。

換顏色時，`heroTintMap()` 依亮度把八階陶土收斂到另一組暗／中／亮三階
（色組定義在 `BLOB_RAMP`）。
外框與眼白不在表裡，所以十種顏色的輪廓都還是暗的、眼睛都還是亮的 ——
直接做色相位移的話，眼白與胸口的記號會跟著染色，十種裡有九種是壞的。

這條規則靠兩邊一起守：`pixelize.py --palette hero` 在轉檔時把顏色限制在十色
體積色盤，`check_art.py` 再驗一次。遊戲換色時把陶土色階重新映射成各玩家色彩的
深、中、亮三階，外框與眼白保持不變。

### 六種體型的頭頂必須在同一列

六種體型共用同一組帽子圖，而帽子畫在固定的位置（不做量測 ——
量測會讓貓的耳朵把帽子頂到畫面外）。所以頭頂高了帽子會陷進頭裡、
低了會浮在半空。

轉檔時用 `--headroom 0.1875` 把頭頂上面那 6/32 的留白裁出來，
`check_art.py` 驗頭頂落在第 4~9 列。要求模型畫的時候對齊某一條線是做不到的，
裁的時候留出來才做得到。

### 為什麼要一支專門的檢查（`check_hero.py`）

接線接錯的話，最常見的下場**不是**畫面壞掉，而是「圖悄悄沒被用到」——
遊戲照跑、看起來跟以前一模一樣，因為它退回了程式畫的那一版。
一張怪物的圖沒接上，打開就看得到；主角有十種顏色 × 六種體型 × 九頂帽子，
沒有人會一個一個看。

所以那一支自己生一組**假的**主角、帽子、武器與盾接進去，逼那條路真的走一遍，
然後問：身體換到了嗎、十種顏色換對了嗎、眼白有沒有被染到、
帽子疊上去了嗎、地上的圖示換到了嗎、八把武器是不是真的八張不同的圖。

有一條**只能靜態掃**：每一層的載入回呼都要作廢快取。
跑起來驗不到 —— 圖在第一幀之前就載完了，那時候快取裡還沒有東西，
所以「忘了作廢」在測試裡沒有症狀。它只在玩家已經在玩、圖才姍姍來遲的時候
咬人（慢網路），而那正是本機永遠測不到的情境。
第一次試著破壞它的時候，跑起來的那 113 條全綠 —— 所以才補了靜態那一條。
假圖是刻意的 —— 它讓這一支在真的圖還沒生出來的時候就能跑，而那正是需要它的時候。

（寫這一支的時候它自己先騙過我一次：讀體型清單的正則少了 MULTILINE，
清單讀成零個、假圖一張都沒生，而「六種體型互不相同」是 `0 === 0`，全綠。
現在清單讀不到會當場停。）
